# D-001 Vite 앱 하나 + 해시 라우팅 + 프로젝트별 lazy

## 한눈에 보기 (코드 몰라도 OK)

상태: [통과] 사용자 확인 완료 (2026-10-25)
무엇을 골랐나: 포트폴리오와 프로젝트 3개를 **앱 하나**에 넣고, 주소의 `#` 뒷부분으로 나눴어요. 각 프로젝트 코드는 그 주소에 들어갈 때 받아요.
왜: 배포는 한 번으로 끝나고, 프로젝트가 늘어도 포트폴리오 첫 화면은 자기 코드만 받으니까 가벼워요. 새 프로젝트의 디자인 페이지를 바로바로 붙일 수 있는 확장성도 이유예요(사용자 확인).

## 개발자 상세

- 상황: 정적 호스팅(Vercel) 하나에 포트폴리오와 실행해 볼 프로젝트 여러 개를 함께 올려야 했어요.
- 근거: `Portfolio/frontend/src/App.tsx` 주석("프로젝트가 늘어도 포트폴리오 첫 화면은 자기 코드만 받는다"), README "프로젝트는 해시 라우팅으로 나뉘고…"

| 후보                                   | 장점                                                            | 단점                                                     |
| -------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------- |
| A. 앱 하나 + 해시 라우팅 + lazy (선택) | 배포 1개, 서버 리라이트 설정 불필요, 새 프로젝트는 라우트 한 줄 | URL에 `#`이 붙음, 검색엔진 색인에 불리, 스크롤 직접 관리 |
| B. 앱 하나 + History 라우팅            | 깔끔한 URL                                                      | 새로고침 시 404를 막는 호스팅 리라이트 필요              |
| C. 프로젝트마다 별도 앱·배포           | 완전 분리                                                       | 배포·도메인·공통 코드 관리가 N배                         |

- 결과로 생기는 제약: 라우터 라이브러리 없이 `useHashRoute` + `subPath` 패턴을 지켜야 해요. 해시가 바뀔 때마다 `scrollTo(0,0)`이 필요하고, 프로젝트 토큰은 접두어로 구분해야 해요.
- 바꿔야 하는 조건: 프로젝트 하나를 독립 서비스로 공개해서 SEO가 필요해지거나, 번들·빌드 시간이 감당 못 할 만큼 커질 때

### 사용자 확인

- **확장성**: remind와 PlanForMe는 개인적으로 쓰려고 아직 넣지 않았어요. 확장할 때 디자인 페이지를 바로바로 넣으려고 이 구조를 골랐어요.
- **예정된 변화**: Accio와 마에스트로는 결국 별도 서비스로 분리해요. 포트폴리오에는 디자인만 있는 부분을 남기고, 링크만 분리된 사이트로 바꿔요. → 분리할 때 이 결정의 적용 범위를 "포트폴리오 + 디자인 시안"으로 줄이는 새 D 문서를 써요.
