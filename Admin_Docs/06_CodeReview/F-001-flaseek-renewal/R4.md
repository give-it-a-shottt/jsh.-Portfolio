## 지적 (있을 때)
- [주의] 상품 사진 스프라이트가 실제로 쓰는 영역에 비해 너무 크다. `products.webp`는 424,748B, 1920×3745(약 719만 화소, 펼치면 RGBA 약 28.8MB)인데, `data.ts`의 crop 15개(상품 12, `GALLERY_EXTRAS`·`PHOTO_REVIEWS`의 추가 2칸, 두께 카드 `napping` 1칸)가 쓰는 화소는 전체의 13.7%뿐이다. 메인(`#/flaseek`)에 처음 들어오면 카드 4장과 두께 카드 3장을 보여 주려고 이 424KB를 통째로 받고 디코드한다. 그래서 `SpriteImage`의 `loading="lazy"`가 아껴 주는 바이트도 없다(모든 칸이 URL 하나를 같이 쓰기 때문). 로컬에서 같은 crop 15개를 각각 WebP q80으로 잘라 보니 합계가 117,466B였다(약 72% 감소). crop들을 감싸는 사각형만 잘라 내도 267,636B다 — 위치: `Portfolio/frontend/src/projects/flaseek/assets/products.webp`, `ui.tsx` `SpriteImage`, `data.ts` `square()`·`GALLERY_EXTRAS`·`PHOTO_REVIEWS`·`THICKNESSES` — 고치는 방법: crop마다 원본 해상도(260px) WebP 파일로 따로 내보내고, `Product.crop` 대신 `image` 경로를 두어 `SpriteImage`를 `<img width height loading="lazy" className="object-cover">`로 바꾼다. 스프라이트를 유지하려면 최소한 crop 영역(대략 x 299~1400, y 301~2619)만 남기고 잘라 낸 뒤 `SPRITE_WIDTH`와 crop 좌표를 그만큼 옮긴다.
- [제안] 상세 화면의 앵커 탭 스크롤 핸들러가 스크롤 이벤트마다 구역 4개에 `getElementById`와 `getBoundingClientRect`를 돈다(값이 같으면 React가 렌더를 건너뛰어서 지금은 체감되지 않음) — 위치: `pages/DetailPage.tsx` 182~204줄 `onScroll` — 고치는 방법: `requestAnimationFrame`으로 한 프레임에 한 번만 계산하거나, 구매바처럼 `IntersectionObserver`(rootMargin으로 오프셋 160/64)로 바꾼다.
- [제안] 상세정보 연출 컷은 첫 화면 아래에 있는데 지연 로딩이 없다(`width`/`height`는 있음, 64,956B) — 위치: `pages/DetailPage.tsx` 388줄 `<img src={detailPreview}>` — 고치는 방법: `loading="lazy" decoding="async"`를 붙인다.
- [제안] 라이트박스가 `bg-black/90` 위에 `backdrop-blur-sm`도 건다. 배경이 90% 검정이라 블러는 거의 보이지 않는데, 화면 전체에 `backdrop-filter`를 걸면 저사양 모바일에서 스크롤·넘기기 때 GPU 부담이 생긴다 — 위치: `Portfolio/frontend/src/portfolio/DesignCaseDetail.tsx` `Lightbox` 루트 div — 고치는 방법: `backdrop-blur-sm`을 빼거나 `bg-black/95`만 쓴다.

## 체크 항목별 근거 (항상 작성)

### 프론트: 불필요한 리렌더링
- 스토어 구독 범위 → `store.ts` `createState`는 `get`이 같은 참조를 돌려줘서 `useSyncExternalStore`가 헛돌지 않는다(21·29·50줄). 구독하는 곳은 셋으로 나뉜다. 장바구니 수는 `layout.tsx` `CartButton`(PC·모바일 2개)만, 토스트는 `ui.tsx` `ToastHost`만, 찜은 `ui.tsx` `WishButton`만 본다. 그래서 장바구니·토스트가 바뀌어도 페이지 전체는 다시 그리지 않는다. 결과: 문제 없음.
- 찜 구독 단위 → `WishButton`이 `useWishes().has(id)`로 Set 전체를 구독해서, 하나를 찜하면 화면의 `WishButton` 전부(리스트 최대 12개 + 상세 2개)가 다시 그려진다. 버튼 안의 SVG 하나만 다시 그리고 개수도 적어서 체감되지 않는다. 결과: 지적하지 않음. 상품이 수백 개로 늘면 `useSyncExternalStore(subscribe, () => wishes.get().has(id))`처럼 불리언으로 구독하면 된다.
- 매 렌더 계산 → `ListPage.tsx` 228~238줄: 카테고리·검색으로 거르는 `scoped`는 `useMemo`이고, 필터·정렬(`results`)은 렌더마다 계산한다. 대상이 12개 이하라 비용이 없다. `sortProducts`는 정렬할 때 복사본(`[...products]`)을 만들어서 원본 `PRODUCTS`를 바꾸지 않는다. `MainPage.tsx` 42줄 `best`, `DetailPage.tsx` 168줄 `product`, 32줄 `Gallery` `images`도 렌더마다 만드는 작은 배열이다. 결과: 문제 없음.
- 화면 다시 시작(key) → `FlaseekApp.tsx` 354~368줄은 `params.toString()`을 `ListPage`·`DetailPage`의 `key`로 준다. 주소 조건이 바뀌면 그 페이지만 새로 마운트되고 `Shell`(헤더·푸터)은 유지된다. 결과: 의도대로 동작하고 낭비가 없다.
- 슬라이더 드래그 → `BeforeAfterSlider.tsx`: `pointermove`마다 `setPosition`이 불리지만 다시 그리는 것은 슬라이더 컴포넌트 하나다. 손잡이는 `transform`, Before 쪽은 `clip-path`로만 움직여서 레이아웃을 다시 계산하지 않는다(316·303줄). 이동마다 부르는 `getBoundingClientRect`(258줄)는 읽기만 하고, 그 사이에 레이아웃을 바꾸는 쓰기가 없어 강제 리플로우가 반복되지 않는다. 결과: 문제 없음.
- 모바일 갤러리 → `DetailPage.tsx` 40줄은 `onScroll`마다 `setCurrent`를 부르지만 값이 같으면 React가 건너뛴다. 결과: 문제 없음.
- 이벤트 리스너 정리 → `DetailPage.tsx` 173~179줄 `IntersectionObserver`는 `disconnect`하고, 198~203줄 `scroll`·`wheel`·`touchstart`·`keydown`은 `removeEventListener`한다. `ListPage.tsx` 135~144줄 `FilterSheet`은 `keydown`을 지우고 `body.overflow`를 되돌린다. `DesignCaseDetail.tsx` `Lightbox`의 `keydown`도 지우고 `overflow`를 되돌린다. 슬라이더의 포인터 이벤트는 React prop이라 따로 정리할 것이 없다. 결과: 문제 없음. 덧붙이면 `store.ts` 54줄 토스트 타이머와 `DetailPage.tsx` 219줄 `requestAnimationFrame`은 언마운트할 때 취소하지 않지만, 구독자가 없는 상태에 값을 넣거나 없는 요소를 찾는 정도라 해가 없다.
