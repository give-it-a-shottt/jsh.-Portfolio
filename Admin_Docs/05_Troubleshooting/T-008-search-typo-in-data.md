# T-008 오타가 데이터에 한 번 적히자 오타 고치기가 멈춤 — "0건일 때만 고친다"의 빈틈

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과]
무엇이 문제였나: 검색 공부 노트를 사이트에 올렸더니, 노트에 예시로 적은 "vmffosvhal", "시스탬"이 데이터가 됐어요. 오타 고치기는 "0건일 때만" 하기로 했는데, 이제 1건이 찾히니 고치지 않았어요. 그래서 "vmffosvhal"을 치면 플랜포미 대신 공부 노트만 나왔어요.
어떻게 해결했나: 1~2개 글에만 있는 드문 말도 고쳐 볼 수 있게 했어요. 단, 검색어가 친 그대로 적혀 있고, 고친 말이 3배 이상 흔할 때만 고쳐요. 맞게 쓴 드문 말("밀리는")은 그대로 둬요.

## 개발자 상세

### 증상 (2026-10-27, 코드는 S6 그대로, 노트 2개만 추가)
| 검색어 | S6 | 노트 추가 후 |
|---|---|---|
| "vmffosvhal" | 플랜포미 사례 7건 | 검색 노트 1건(정답 없음) |
| "디자인 시스탬" | 디자인 시스템 사례 | 0건 |
| "안드로이드 앱"(없어야 함) | 0건 | 검색 노트 1건 |
- 시험지 점수: 상위 3 적중률 95% → 90%, 엉뚱한 결과 0% → 17%

### 원인
- 새 노트 [fe-search-algorithm](../../Portfolio/frontend/src/portfolio/noteData/front.ts)이 "vmffosvhal → 플랜포미", "시스탬 → 시스템", "안드로이드 앱 ≠ 아무 앱"을 예시로 담고 있어요. 검색에 대한 글이 검색어를 데이터로 만든 거예요.
- S4의 규칙은 "원래 말로 찾히면 고치지 않는다"였어요. 오타가 데이터 어딘가에 한 번만 있어도 이 규칙은 무너져요.
- "안드로이드 앱"은 오류가 아니에요. 그 말이 실제로 노트에 들어 있으니 찾는 게 맞아요. 시험지의 정답("없어야 함")이 데이터 변화로 틀려진 거예요.

### 해결 (사용자 결정: 흔한 쪽으로 고치기 + 없어야 함 검색어 교체)
- [search.ts](../../Portfolio/frontend/src/portfolio/search.ts)의 `findWord`:
  - 0건: 예전과 같이 고쳐요.
  - 1~2개 문서(드문 말): 두 조건을 다 채울 때만 고쳐요.
    - 검색어가 **친 그대로** 그 글들에 적혀 있다(조사·어미를 뗀 모양으로만 걸린 게 아니다)
    - 고친 말이 원래 말보다 **3배 이상** 많은 문서에 있다
- 시험지 Q39 "안드로이드 앱" → "스위프트 앱". 사이트 데이터에서 직접 찾아 없는 말임을 확인했어요(검색을 돌려 보고 고르지 않았어요). 바꾼 이유는 queries.json의 memo에 남겼어요.

### 시행착오 (결과를 보고 고친 것)
1. 처음엔 "고친 말이 3배 이상 흔하면"만 넣었어요. 그러자 상위 3 적중률이 97%로 올랐는데, 들여다보니 "날짜가 하루 밀리는 버그"의 "밀리는"을 "미리"로 잘못 고친 덕이었어요. 진짜 개선이 아니라서 버렸어요.
2. 다음엔 "드문 말이 나온 글에 고친 말도 함께 있으면(오타를 예시로 든 글)"을 넣었어요. 그런데 "밀리면"이 든 플랜포미 글에 우연히 "미리"도 있어서("밀렸거나 미리 했…") 그대로 통과했어요. 우연에 기대는 조건이라 버렸어요.
3. 마지막으로 "친 그대로 적혀 있을 때만"으로 바꿨어요. "vmffosvhal", "시스탬"은 그대로 적혀 있고, "밀리는"은 어미를 뗀 "밀리"로만 걸려요. 이 차이로 셋이 갈려요.
- ⚠️ 세 조건 모두 이번 사례를 보고 만들었어요. 그래서 처음 보는 검색어로 다시 쟀어요(아래).

### 결과
| 지표 | S6 | 노트 추가 후(고치기 전) | 고친 뒤(S6b) |
|---|---|---|---|
| 상위 3 적중률 (시험지 39개) | 95% | 90% | 95% |
| 엉뚱한 결과 (없어야 함 6개) | 0% | 17% | 0% |
| 처음 보는 검색어 10개 | 50% | 50% | 50% |
| 자동완성 / 관련 검색어 | 100% / 100% | 같음 | 같음 |
- 잘못된 고치기("밀리는 → 미리")는 없어요. "히스토그램", "웨이팅"처럼 맞게 쓴 드문 말도 그대로 찾아요.

### 재발 방지
- 데이터(노트·사례)를 추가한 뒤에도 `npm run search:eval`을 돌려요. 이번처럼 코드가 그대로여도 점수가 바뀔 수 있어요.
- "없어야 함" 검색어는 데이터에 그 말이 생기면 정답이 바뀌어요. 바꿀 때는 이유를 memo에 남겨요.

### 배운 것
- 검색 엔진에서 문서는 고정된 게 아니에요. 검색에 대한 글이 올라오면 그 글이 검색 결과를 바꿔요(메타 콘텐츠).
- "0건일 때만"처럼 깔끔한 규칙도 데이터가 바뀌면 빈틈이 생겨요. 실제 맞춤법 교정기가 "더 흔한 쪽"을 보는 이유예요.
- 점수가 올랐다고 바로 믿지 않고, 왜 올랐는지 들여다봐야 해요. 이번 97%는 틀린 고치기 덕이었어요.
