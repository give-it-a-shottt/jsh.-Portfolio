## 지적 (있을 때)
- [제안] techlearn 썸네일 13장이 모두 JPEG(합계 267,804B)다. 사이트의 다른 사례 이미지는 webp를 쓴다. 홈 첫 방문에 hero-msa(43,022B)와 인기 강좌 4장(course-1~4, 합계 142,097B)으로 약 185KB를 받는다. 크기 자체는 작아서 급하지 않다. — `projects/techlearn/assets/*.jpg`, `data.ts` 6~9줄, `lectures.ts` 1~9줄, `screens/HomeScreen.tsx` TrendCard — 같은 해상도로 webp로 바꿔 import 경로만 고친다(30% 안팎 줄어들 것으로 추정, 측정은 안 함).

## 체크 항목별 근거 (항상 작성)
- 프론트 · 번들 크기 → `App.tsx`의 `lazy(() => import("./projects/techlearn/TechlearnApp"))`로 따로 나뉜다. `npm run build` 결과 `TechlearnApp-*.js` 103.59 kB (gzip 28.01 kB)이고, 이 중 4KB 미만 SVG 39개(약 31KB)가 data URI로 들어 있다. 메인 청크에는 `routes.ts`의 `techlearnHref`와 `PROJECTS` 칩만 들어간다(빌드 결과를 grep으로 확인). HEAD를 scratchpad에 따로 빌드해 비교하니 메인 JS 619.09 → 620.37 kB(gzip +0.58 kB)로 거의 그대로이고, 500kB 경고는 이번 변경 전부터 있었다. 공용 CSS는 149.98 → 166.05 kB(gzip 24.20 → 26.21 kB)로, techlearn의 Tailwind 클래스와 `tl-*` 토큰이 모든 화면이 받는 한 파일에 들어가서 늘었다. Tailwind 한 파일 구조는 원래 그대로라 지적하지 않았다.
- 프론트 · 이미지 최적화 → `ls -la`와 JPEG 헤더로 확인했다. course·hero·detail 6장은 512×279(29~43KB), lec-* 7장은 294×160 또는 235×128(4~9KB)이라 표시 크기에 비해 크지 않다. `CourseCard`(components.tsx), `LectureCard`(CourseListScreen.tsx)는 `loading="lazy"`가 있다. 히어로 `TrendCard`, 상세 큰 썸네일, `EnrollCard` 이미지는 lazy가 없지만 첫 화면이거나 첫 화면 근처라 괜찮다. 상세 화면은 모바일 썸네일과 PC 카드가 CSS로 하나만 보이는데, 둘 다 `lecture.cover ?? lecture.thumbnail`로 같은 파일이라 두 번 받지 않는다. 카드 이미지는 높이가 고정된 상자(h-[153px], h-48, h-[203px], aspect-video) 안에 있어서 width/height가 없어도 레이아웃이 밀리지 않는다. JPEG 형식 문제는 위 [제안]으로 적었다.
- 프론트 · 불필요한 리렌더링 → `store.ts` `useTechlearn`은 구독 함수가 모듈 함수라 매번 다시 구독하지 않고, 스냅샷은 바뀔 때만 새 객체(`setState`)가 되어 무한 렌더가 없다. 구독하는 곳은 `CourseListScreen`과 `useEnroll`뿐이고 Header는 구독하지 않는다. 토스트 `EnrollToast`의 타이머 effect는 `[toast, onDone]`에 걸려 있는데, `onDone`은 `useCallback`(hooks.ts `clearToast`)이고 toast는 `TOAST_BY_STATUS` 상수 객체라 부모가 다시 그려져도 타이머가 다시 시작되지 않는다. 화면을 떠나면 cleanup이 타이머를 지운다. `EnrollModal`은 `confirming`일 때만 그려지고 `showModal`은 마운트할 때 한 번만 부른다. 검색 입력(`useCourseSearch`)은 Header와 Hero 각자의 state라 글자를 칠 때 그 조각만 다시 그린다. `Curriculum`의 `matchMedia`는 useState 초기값이라 한 번만 돈다.
- 프론트 · 렌더마다 도는 무거운 계산 → `CourseListScreen`의 `LECTURES.filter`(8개), `BestCourses`의 `COURSES.filter`(4개), `lessonCount`·`totalLength`(강 수십 개)는 렌더마다 돌지만 데이터가 작아서 memo가 필요 없다. `SearchHome.tsx`의 `RECENT`는 모듈을 처음 불러올 때 한 번만 계산한다(사례 26개 `rankCases` 정렬 3번과 노트 filter). 홈에서 `RecordCard` 이미지 카드 6장이 빠져 홈이 받는 이미지가 줄었다. `PortfolioHeader.tsx`(감싸는 div 추가)와 `PortfolioFooter.tsx`(링크 1개 상수)는 정적이다.
- 프론트 · 과도한 API 호출 → 실제 네트워크 호출은 없다. `api.ts` `enrollCourse`는 900ms setTimeout으로 흉내만 낸다. `useEnroll.open`이 `state === 'available'`일 때만 모달을 열고, 신청 중에는 상태가 `pending`이라 두 번 요청하지 않는다.
- 프론트 · 스크롤 중 그리기 부담 → sticky 헤더 `backdrop-blur-[6px]`, 카드마다 난이도 배지와 찜 버튼 `backdrop-blur-[4px]`(목록 화면 최대 16개), 히어로의 큰 `blur-[32px]`·`blur-[50px]` 장식이 있다. 실제로 느린지는 미확인 (이유: 저사양 모바일에서 Performance 패널로 재 보지 않음). `animate-ping`은 transform·opacity 애니메이션이고 `motion-reduce`를 지킨다.
- 백엔드 · N+1 쿼리 → 해당 없음 (이유: 백엔드 변경 없음, `git status`에 Portfolio/backend 파일 없음, techlearn은 코드 안 목업 데이터만 씀).
- 백엔드 · 인덱스 → 해당 없음 (이유: DB를 쓰지 않음, feature.md 데이터 항목 "없음").
- 백엔드 · 페이지네이션 → 해당 없음 (이유: 서버 목록 API 없음. 강의 8개를 코드에서 바로 그림).
- 백엔드 · 무거운 작업의 동기 처리 → 해당 없음 (이유: 서버 작업 추가 없음).
