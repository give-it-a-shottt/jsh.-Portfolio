## 지적 (있을 때)
- [제안] 타입 주석 두 개가 서로 "맨 앞 칸"이라고 말해요. `sections`(207줄)는 "맨 앞 칸부터", `story`(209줄)는 "있으면 맨 앞 칸에"인데, 실제로는 `sections`가 먼저 그려지고 `story`는 그 다음이에요. 지금 둘을 함께 쓰는 사례는 없지만, 다음에 둘 다 쓰면 주석을 믿고 순서를 잘못 짚을 수 있어요. — 위치: `portfolio/data.ts` `DesignCase.story` 주석, `DesignCaseDetail.tsx` 357~368줄 — 고치는 방법: `story` 주석을 "sections 다음 칸에 보여준다"로 바꿔요.
- [제안] data-model.md에 새 타입이 없어요. 사례 목록 행에는 `design?: DesignCase`까지만 있고, 이번에 생긴 `DesignSection`과 `DesignCase.sections`가 빠졌어요. level 4를 "분류마다 하나까지"로 바꾼 규칙도 rank.ts 주석에만 있어요. — 위치: `Admin_Docs/01_Overview/data-model.md` "1) 프론트 정적 데이터" 표 — 고치는 방법: 표에 `DesignCase { …, sections?: DesignSection[] }`를 적고, 검색 순위 행에 "4는 분류마다 하나"를 한 줄 더해요.

## 체크 항목별 근거 (항상 작성)
- 프론트 · 컴포넌트 책임 → `DesignCaseDetail.tsx` 357~368줄을 봤어요. `sections`를 `map`으로 돌리면서 기존 `ScreenSection`(163줄~)을 그대로 다시 써요. 새 컴포넌트는 없어요. 상세 화면은 칸 순서만 정하고, 카드 목록·라이트박스는 `ScreenSection`이 맡는 구조가 그대로예요. 문제 없음.
- 프론트 · 폴더 구조 → architecture.md "프론트 폴더"의 `portfolio/`(data.ts, rank.ts, *Detail) 안에서만 바뀌었어요. 이미지는 `portfolio/assets/design/jsh-ds/`에 있고, 형제 폴더(accio, flaseek, gameprobe 등)와 같은 "사례별 폴더" 패턴이에요. `projects/`나 `shared/`는 건드리지 않았어요. 문제 없음.
- 프론트 · 상태 위치 → 새 상태는 없어요. `ScreenSection` 안의 로컬 상태(`openIndex`, `edges`)를 칸마다 따로 써요. 전역·서버 상태가 필요한 데이터가 아니라서 맞는 위치예요.
- 프론트 · 데이터 타입 설계 → `data.ts` 185~192줄 `DesignSection { title, description, items: DesignVariant[], device? }`는 기존 `DesignVariant`를 재사용해요. `device`는 `'mobile' | 'desktop'`이라 `ScreenSectionProps.device`(154줄)의 부분 집합이에요. 기본값은 `section.device ?? 'desktop'`으로 주석("없으면 데스크톱 카드")과 같아요. `sections`는 선택 필드라 다른 Design 사례 7개는 그대로 돌아가요.
- 프론트 · 키·id 충돌 → 칸 `key`는 `section.title`이고, 이 사례의 칸 제목 8개는 모두 달라요(G 두 칸도 "PC"/"모바일"로 달라요). `id`는 `section-${index}-title`이라 기존 `story-title`, `screens-title` 등과 겹치지 않아요. 칸 안 `key={item.label}`도 칸마다 라벨이 겹치지 않아요.
- 프론트 · 순위 규칙 → `rank.ts` 14~15줄 `rankCases`는 level → 날짜순 그대로예요. 코드는 안 바뀌고 주석만 "분류마다 하나까지"로 바뀌었어요. level 4가 Accio(2025.11)와 이 사례(2026.10) 두 개라서 전체·홈(`SearchHome.tsx` 12줄 `rankCases(CASES).slice(0, 6)`)에서는 이 사례가 첫 칸, Accio가 둘째 칸이에요. Design 탭(`SearchResults.tsx` 171·175줄, 분류로 거른 뒤 정렬)에서도 첫 칸이에요. F-006 문서 "실제 구조"와 일치해요. "분류마다 하나"는 코드로 막지 않고 약속으로만 둬요(지금 데이터는 지킴).
- 프론트 · 다른 소비처 → `.design`을 읽는 곳은 `DesignCaseDetail.tsx`와 `PortfolioApp.tsx` 110줄(유무 판단)뿐이에요. `sections`를 따로 읽어야 하는 곳은 없어요. 데모가 없는 사례라 `DESIGN_DEMOS`에 등록하지 않은 것도 맞아요.
- 백엔드 · 레이어 분리 / 의존 방향 / 라우터의 로직 → 해당 없음 (이 커밋은 `Portfolio/frontend/src`와 Admin_Docs만 바꿨고 `Portfolio/backend`는 그대로예요. `git show 9439b24 --stat`으로 확인)
- 데이터 · data-model.md와 실제 모델 일치 → data-model.md는 이 데이터를 "코드 안에 직접 적은 목록"으로 분류해요. 이 사례도 같은 방식이라 분류는 맞아요. 다만 표에 `DesignSection`·`sections`가 없어요(지적 2).
- 데이터 · 관계·제약(외래키, NOT NULL, UNIQUE) → 해당 없음 (DB 테이블이 없어요). 비슷한 제약을 확인했어요. `slug: 'jsh-design-system'`과 `code: 'DESIGN 08'`은 기존 Design 사례(01~07)와 겹치지 않아요. `href`는 `#/case/{slug}` 규칙과 같아요.
